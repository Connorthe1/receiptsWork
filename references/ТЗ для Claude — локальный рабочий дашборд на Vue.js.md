# Техническое задание: локальный рабочий дашборд на Vue.js

Необходимо разработать современный локальный веб-интерфейс для хранения и быстрого использования рабочей информации.

Основной стек:

- Vue 3
- Composition API
- Vite
- JavaScript или TypeScript
- Pinia для состояния
- Vue Router
- Данные должны храниться локально
- На первом этапе backend не нужен
- Для хранения использовать IndexedDB либо localStorage, предпочтительно IndexedDB
- Интерфейс должен корректно работать после перезагрузки страницы без потери данных

Приложение предназначено для персонального использования на локальном компьютере.

## 1. Общая концепция

Интерфейс должен представлять собой dashboard в блочном/card-based стиле.

Слева желательно сделать постоянный sidebar с навигацией.

Пример структуры:

- Главная
- Раздел 1
- Раздел 2
- Раздел 3
- + Новый раздел
- Настройки

Главная страница содержит общие данные.

Дополнительные разделы создаются пользователем самостоятельно и используются под отдельные работы / проекты.

Каждый раздел имеет собственное название, собственные данные и при необходимости собственный список ссылок.

При этом общий список Email-аккаунтов должен быть доступен как на Главной странице, так и внутри каждого созданного раздела.

---

# 2. Главная страница

Главная страница должна состоять из отдельных независимых блоков.

Блоки желательно оформить карточками.

Желательно предусмотреть возможность в будущем:

- менять порядок блоков;
- скрывать блоки;
- сворачивать блоки;
- изменять их размер.

На первом этапе drag-and-drop необязателен, но архитектура компонентов должна позволять добавить его позже.

---

# 3. Блок «Почты»

Необходимо хранить список Email-аккаунтов.

Для каждой записи:

- Email / логин
- Пароль
- Опциональное название / комментарий
- Статус
- Дата создания
- Опциональные заметки

Пример:

Account 1  
Email: example@gmail.com  
Password: ********  
Комментарий: Main account

Функциональность:

- добавить аккаунт;
- редактировать;
- удалить;
- копировать Email отдельной кнопкой;
- копировать пароль отдельной кнопкой;
- копировать Email + Password вместе;
- показать / скрыть пароль;
- поиск по аккаунтам;
- отображать короткий toast после копирования: «Скопировано».

Пароль по умолчанию должен быть скрыт.

Например:

example@gmail.com     [Copy]
••••••••••••          [Show] [Copy]

Кнопка копирования должна копировать значение непосредственно в clipboard.

# 4. Статусы Email-аккаунтов

У каждого Email-аккаунта должен существовать общий статус:

- Active
- Inactive

Но дополнительно каждый отдельный рабочий раздел должен иметь возможность отметить конкретную почту как неактивную именно для этого раздела.

То есть:

Email существует в едином глобальном списке.

Например:

email1@gmail.com
email2@gmail.com
email3@gmail.com

В разделе «Работа A»:

email1@gmail.com — Active  
email2@gmail.com — Inactive  
email3@gmail.com — Active

В разделе «Работа B»:

email1@gmail.com — Inactive  
email2@gmail.com — Active  
email3@gmail.com — Active

Изменение статуса внутри одного рабочего раздела НЕ должно изменять статус этой же почты в других разделах.

Для переключения использовать понятный toggle / switch либо radio-кнопку.

Предпочтительный вариант UX:

[● Active] / [○ Inactive]

или обычный switch.

Неактивные почты визуально должны отличаться:

- уменьшенная opacity;
- серый статус;
- строка может быть слегка затемнена.

Также должна быть возможность:

- показывать все;
- показывать только Active;
- показывать только Inactive.

# 5. Блок «Важная информация»

Универсальный блок для данных, которые часто нужны под рукой.

Пользователь самостоятельно создает записи формата:

Название → Значение

Например:

Phone → +1 555 000 0000  
Default password → ExamplePassword123  
PIN → 1234  
Username → example_user  
Reference ID → ABC123

Для каждой записи:

- название;
- значение;
- комментарий — опционально;
- секретное значение — true/false.

Если запись отмечена как секретная, значение по умолчанию скрывать.

Функции:

- добавить;
- редактировать;
- удалить;
- копировать значение;
- показать / скрыть секретное значение.

Не нужно жестко привязывать блок только к номеру телефона или паролю.

Он должен быть универсальным key-value блоком.

•••

- редактировать;
- удалить;
- копировать номер;
- копировать имя;
- копировать expiry;

# 26. Важные архитектурные требования

Не дублировать глобальные Email внутри Workspace.

Использовать нормализованную модель данных.

Например:

emails:
[id=1, id=2, id=3]

workspaceEmailStatuses:

workspace=1, email=1, active  
workspace=1, email=2, inactive  
workspace=2, email=1, inactive

Таким образом один Email может иметь разные состояния в разных Workspace.

Это является одним из основных требований приложения.

# 27. Требования к коду

Код должен быть:

- понятным;
- модульным;
- расширяемым;
- без огромных монолитных компонентов;
- без дублирования;
- с переиспользуемыми composables;
- с понятными названиями переменных и компонентов.

Сначала создай структуру проекта и модель данных.

После этого реализуй интерфейс поэтапно.

Не помещай весь проект в один файл.

После завершения базового функционала проверь:

- сохранение после reload;
- создание нескольких workspace;
- разные статусы одной и той же почты в разных workspace;
- Copy;
- редактирование;
- удаление;
- маскирование секретных данных;
- переключение Dark / Light Mode.
